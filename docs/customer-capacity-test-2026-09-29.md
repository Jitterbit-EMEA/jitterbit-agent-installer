# Customer installer and 10-agent limit check — 2026-09-29

**Scope:** RC9 offline qualification and read-only QA baseline. No agent was uninstalled, reinstalled, added to, or deleted from Harmony during this check.

The designated Ubuntu 24.04 QA VM was reached using the previously pinned SSH host key. Its installed PA remained `12.10.1.1`; the bundled RC7 status command reported package `INSTALLED`, agent connection `True`, and core services healthy `True`. This confirms the starting host remained healthy. It does **not** establish the current Harmony group count or licensed maximum.

The synthetic runtime test `test_ten_successful_slots_then_eleventh_capacity_failure` executed ten clean registration workflows with a fake backend. Each completed with `harmonyRegistered=True`. An eleventh workflow received a vendor-style maximum-agents log line, returned `AGENT_CAPACITY_REACHED`, did not claim Harmony registration, and retained its registration input for controlled diagnosis. A separate launcher test confirmed the capacity error becomes a plain-language instruction to review unused stopped agents and licensed capacity. These tests exercise the code's failure path; they do **not** prove a live eleventh registration against Harmony or an API-level capacity precheck.

The repo's complete uninstall removes local PA state but does not remove the Harmony agent identity. With `deregisterAgentOnDrainstop=false`, a stopped agent remains in the group. Jitterbit documents both group and organization limits and requires a suitable stopped or unregistered state before deleting an agent: [registration behavior](https://docs.jitterbit.com/agent/register/), [capacity troubleshooting](https://docs.jitterbit.com/getting-started/troubleshooting/). Repeating live uninstall/reinstall to force the eleventh failure would consume group slots and could block the working QA agent's replacement. A dedicated disposable group with known capacity and an approved cleanup method is required for that live demonstration.
