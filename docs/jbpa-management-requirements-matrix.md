# JBPA Management Requirements Matrix

Updated 2026-10-14. 120 requirements across 11 areas.

Preserve current MCP-driven onboarding, the minimal management bootstrap, file/profile/group relationships, agreed baseline behavior and deferred upgrades. This is planning, not a runtime implementation or deployment claim.

The [canonical JSON](jbpa-management-requirements.json) owns the requirement IDs, scope, decision status, implementation status, contract and acceptance criteria. This readable matrix is generated from it. Update the JSON first, then run `python scripts/management/render-requirements-matrix.py`.

## MCP driven setup and minimal bootstrap

| Entry point | Customer interaction | Bootstrap requirement |
| --- | --- | --- |
| Minimal management bootstrap | Deploy the management service and required authenticated Jitterbit integration | Must precede MCP onboarding |
| Jitterbit MCP guided onboarding | Product-owned Markdown guide plus structured options, file IDs, configuration, validation and execution tools | Primary customer onboarding interface; no local AI shell access |
| Jitterbit file upload route | Capable client/uploader or private upload page sends bytes through APIM/Studio to management storage | AI receives safe file references, not private-key contents |

The backend owns setup state and validates every field/mapping. Markdown tells the AI what to ask; it is neither executable configuration nor an authorization mechanism. The previously proposed AI-assisted terminal installer is superseded as the primary customer flow.

## Multiple host selection example

Illustrative selections only; these are not actual customer hosts or credential files. The AI uses MCP options to ask for the host count, discover staged/uploaded files, then repeat host-specific questions. It can offer an explicit apply-to-all default with overrides.

| Host | Selected SSH file ID | Selected registration profile | Setup state |
| --- | --- | --- | --- |
| Host 1 | key-01 | group-a-profile | Awaiting validation |
| Host 2 | key-03 | group-a-profile | Awaiting validation |
| Host 3 | key-02 | group-b-profile | Awaiting validation |
| Host 4 | key-04 | group-b-profile | Awaiting validation |

If four private keys are staged, the setup options API shows all four usable candidates by safe name/ID. Ask which applies to each host; do not infer the answer from names or host order. Apply the same typed selection to certificates and other optional configuration. Reuse across hosts is an explicit choice.

## Changing the group being managed

Selecting another authorized group/profile changes discovery and future selections. A submitted job keeps its recorded target, group and profile revision. An installed PA is not moved, re-registered or reinstalled by changing the active context. Moving an installed PA is a separately qualified and authorized lifecycle operation.

## Requirement matrix

Baseline rows are first-release requirements. Qualification-required options must remain unavailable until their implementation and evidence exist. Observability is deferred until baseline validation. Existing QA evidence is scoped and does not certify the proposed management product.

## Deferred skill security phase

The immediate security scope is the JBPA skill through Codex/Claude, not an MCP redesign. SEC-SKL-001 through SEC-SKL-014 are agreed design only: implement last among selected functional phases and only on an explicit user request. Production monitoring is read-only; install, upgrade, uninstall and deregistration require a separate approval workflow. No skill/runtime controls are changed by this matrix. Production access remains gated on implementation and qualification. See the [skill security architecture](skill-security-architecture.md).

## Decision changes

- 2026-10-07: MCP-driven onboarding replaces the proposed AI-assisted installer as the primary customer flow. Minimal management bootstrap remains a prerequisite; Markdown guides questions; validated APIs and Jitterbit file transfer own state/data/execution. Superseded: Local AI shell/TTY adapter and installer-led initial target configuration as the required onboarding path

- 2026-10-07: Customer explicitly runs the local management installer on a bare VM; only after management readiness is Jitterbit MCP configured. Complete runtime parameters belong to this installer; target onboarding then uses MCP. Superseded: Any implication that MCP or an existing management API installs the management stack

- 2026-10-08: Record high-volume PA/host metrics and TranDb execution fields in deferred UPG-001 canonical contracts. Current install planning uses PostgreSQL READY backlog directly; the previous JBMQ/outbox/dispatch design is superseded for baseline. Superseded: Mandatory JBMQ/outbox delivery after durable management job acceptance; one unbounded canonical payload for all future data

- 2026-10-13: Record skill-specific security as the final selected implementation phase, only on explicit request. Production monitoring is read-only; install, upgrade, uninstall and deregistration use an independent approval workflow. This is not an MCP implementation change. Superseded: Any assumption that conversational permission or workstation-held production SSH credentials alone authorize production lifecycle execution

- 2026-10-14: Vendor installer owns normal upgrade configuration/startup; JBPA triggers and monitors without restart or deployment repair. Explicit downgrade uses uninstall/fresh reinstall. Superseded: Proposal to disable vendor automatic startup, rebuild Axis routinely, or restart from upgrade verification
