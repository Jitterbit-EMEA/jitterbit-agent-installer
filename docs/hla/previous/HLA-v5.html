JBPA Management Platform

High-level architecture | Customer-deployable Private Agent lifecycle management

Revision5.0

This build is a reusable management product that customers deploy in their own environment. It exposes supported JBPA actions through Jitterbit MCP, delivers requests through API Manager, Studio and JBMQ, and executes them from a dedicated Linux management host against explicitly named target VMs.

The management host runs a REST API, a background worker, PostgreSQL and an HTTPS entry point in containers. The existing JBPA caller remains the lifecycle engine. Target hosts use their existing SSH access; no additional listening service is introduced on the PA hosts.

What is built
A deployable management platform

Versioned containers, configuration contracts, job APIs and a matching Jitterbit project kit.

How it works
Durable asynchronous execution

Accept and identify the job, queue delivery, execute through SSH, retain the validated result.

What it delivers
Repeatable customer operation

A standard install/upgrade/recovery experience across permitted hosts and independent customer deployments.

Proposed product architecture. The management stack is not yet implemented or production-qualified; scoped JBPA evidence and release gates are documented in the qualification section.

Purpose, outcomes and design boundaries

The design connects customer deployment, agent management and operational accountability.

Revision5.0

Installations may take several minutes and may restart or remove the target agent. The component initiating the change must therefore remain available independently of that target. The first AI/API call returns durable acceptance and a job ID; execution and result retrieval continue independently of the conversation.

Each customer operates a separate deployment of the same product release. Customer-specific inventory, credentials, certificates, access policy and Harmony configuration are external to the image. The product starts after target infrastructure has been provisioned.

Non-negotiable boundaries

No arbitrary host or shell command is accepted from an AI request. Install does not silently become upgrade or reinstall. Local uninstall does not delete Harmony records. A timeout does not prove the remote action failed. Supported OS/package tuples, upgrade edges and artifact provenance govern production execution.

API technology - reuse the Python investment

FastAPI defines the contract; the separate worker owns long-running execution.

Revision5.0

Python + existing JBPA

WHY: the repository already contains lifecycle adapters, release validation and a structured SSH caller.
VALUE: wrapping the fixed caller preserves its checks instead of duplicating install logic.
REUSE: API and worker share request/result models and one application image. Other clients can use the same REST API.
TRADEOFF: remote attempt recovery and a production execution profile still require code changes.

FastAPI + Pydantic

WHY: typed request/response models support validation and OpenAPI/JSON Schema generation. [T1, T2]
VALUE: reject invalid target/action/version input early and keep Jitterbit transformations aligned with the API.
REUSE: model definitions become documentation, tests and client schemas.
TRADEOFF: validation is not authorization; action/target checks remain application responsibilities.

Uvicorn + separate worker

WHY: Uvicorn serves the ASGI API; a separate process claims durable READY jobs.
VALUE: API restarts do not erase accepted execution work.
REUSE: the same worker image can run with different permitted inventories.
TRADEOFF: process restart does not prove a remote mutation stopped; reconcile its original attempt.

Alternatives considered

Flask can serve this API but needs more explicit schema integration. Node.js/Go would introduce another language around a Python execution engine. FastAPI in-memory background tasks are insufficient as the durable job mechanism. A new Celery/Redis stack is not required for the initial product.

Database technology - durability and coordination

PostgreSQL is selected for the product baseline, including customers with more than one worker.

Revision5.0

PostgreSQL

WHY: transactional creation of job + outbox, uniqueness for idempotency, and controlled concurrent claims. [T3]
VALUE: results and ownership survive application restarts; uncertain actions remain visible.
REUSE: customers can use the bundled DB or a qualified external PostgreSQL service.
TRADEOFF: backups, migrations and restoration are required operations.

Worker ownership

WHY: a queue can redeliver and a worker can fail mid-installation.
VALUE: canonical-host ownership prevents simultaneous lifecycle changes across aliases and workers.
REUSE: the same contract works for one worker or a qualified expanded deployment.
TRADEOFF: lease expiry is only a warning; it never independently authorizes replay.

SQLAlchemy + Alembic

WHY: explicit transactions and schema changes tracked as released migrations.
VALUE: every customer can upgrade through a tested version sequence.
REUSE: application repositories, migration tests and database compatibility checks are shared product code.
TRADEOFF: migrations must be reviewed and run once; database portability is not promised merely by using an ORM.

Why not SQLite or another broker?

SQLite fits a small local tool, but PostgreSQL is the deliberate shared-service baseline for this product. JBMQ already handles external delivery; the parent database holds accepted worker jobs. A second broker would add deployment and recovery responsibilities without a demonstrated requirement.

WHY: the target already has an established remote administration interface.

Kubernetes introduces a control plane and operational skills that the first customer package does not require. Managed PostgreSQL and existing reverse proxies are optional integration profiles. Acceptance and delivery guarantees

These rules connect the sequence diagrams to the durable job contract.

Revision5.0

Lost response handling

The client may lose a response after the database commits. It retries with the same request identity. The job may already be queued or running, so a fresh identity must not be substituted merely because the initial HTTP call failed.

Failure classification

Transient delivery problems receive bounded delayed retries. Invalid, unauthorized or inconsistent references go to delivery quarantine/dead-letter review. A known installation failure is a valid business result, not a delivery failure.

The original MCP request returns after durable acceptance. Queue acknowledgements and remote execution outcomes are different facts. Neither a lost HTTP response nor an expired worker lease justifies replaying a mutation.

Execution lifecycle

ACCEPTED_PENDING_DISPATCH -> READY -> RUNNING -> SUCCEEDED or FAILED. An uncertain remote outcome enters NEEDS_RECONCILIATION while host ownership is retained. Queue publication is recorded separately and cannot regress a running or completed job.

Idempotency and results

Same key + same canonical request returns the same job. Same key + changed parameters is a conflict. Diagnostic status does not prove identity-aware Harmony health. Requested/resolved versions, artifact digest, worker release and attempt identity support reproducible diagnosis.

Queue reliability and publication recovery

The request queue buffers delivery; the parent database preserves the business record.

Revision5.0

Acknowledgement and retry

ACK only after the parent commits READY or confirms compatible prior acceptance. Use bounded delayed retry. Do not wait for installation before ACK. The queue design must respect the customer tier and avoid assuming additional retry queues are licensed. [J1, J4]

Service constraints

JBMQ documents a 30-minute acknowledgement timeout and a maximum message TTL of 10 days. Monitor backlog and oldest job; PostgreSQL is the historical source. New submissions require the parent and DB because durable job creation precedes queue publication. [J1]

Identity is enforced in the service

A shared integration identity receives only its explicit scope. Delegated user identity must be verified, not trusted from model-generated headers. Separate submit, relay, dispatch, read and administrative permissions. Rotate access tokens, TLS and SSH material through tested procedures.

A timeout means the outcome may be unknown; it does not mean the target is unchanged.

Required adapter improvement

Before any mutation, bind a stable job/attempt identity to the remote command and evidence path. The current synchronous caller discovers some evidence after execution; the product must make interrupted attempts discoverable through SSH without adding a target daemon or port.

Execution guarantee

Delivery is at least once and requests are idempotent. Exactly-once remote mutation is not claimed. Safety is provided by canonical-host coordination, remote locking, stable evidence and reconciliation. Generic executing-job cancellation and package rollback are excluded until qualified.
